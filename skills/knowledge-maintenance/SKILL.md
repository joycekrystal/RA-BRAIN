Read ../delivery-standards/references/shared-rules.md and ../delivery-standards/references/templates.md. Locate the existing knowledge index and source documents before creating duplicates. Organize business overview, domain glossary, capabilities, feature specifications, architecture, ADRs, API/data contracts, design references, engineering standards, test strategy, operations and release history. Keep one canonical document per concern; link to source systems rather than copying entire workspaces. Record document owner when known, status, source revision and review date. Compare a bounded set of changed code/tickets/designs to related documentation and show concrete conflicts or stale sections. Draft targeted updates and record decisions in ADRs with context, options, decision and consequences. Preserve history and approved decisions; mark supersession explicitly. Maintain a change log and criterion-to-test traceability. Propose refinements to general plugin standards separately from project facts. No background monitoring, automatic sync, or persistent storage is provided by this package.

## Create or update the application knowledge base

Read references/knowledge-base.md for the workflow and reusable structure. Treat a knowledge base as maintained application documentation with an index of canonical references, not as implicit assistant memory. Preserve existing skill inputs and workflows: a supplied page, repository, feature or bounded drift-review request is sufficient to start. Do not require a new host-specific tool, mandatory directory migration or unrelated documentation rewrite.

1. Identify the application and existing canonical index from the user's context, supplied page ancestry/links or repository documentation. Read existing material before creating more. Use the selected application repository or Confluence destination; keep application facts out of the generic plugin repository. If no destination is known, prepare a clearly labeled draft and resolve the destination only when needed for persistence.
2. Maintain an index mapping each concern to one canonical document, its scope, owner when known, status, source ID/URL or path, exposed revision/commit and review date. Reuse current pages/files and link additional evidence rather than cloning it. A source-of-truth designation establishes intended requirements or decisions; code, runtime data and test evidence can disagree and must be compared explicitly.
3. Capture confirmed business rules and user-approved decisions durably. Label facts, accepted decisions, proposals, assumptions, unresolved questions, superseded requirements and unverified implementation separately. Preserve decision history, source provenance and criterion identifiers. A user's answer to one question does not resolve adjacent unanswered questions.
4. Create or update only the artifacts justified by the task: context, glossary, capability index, feature rules/criteria, contracts, architecture/ADRs, design references, engineering standards, verification, operations and release history. Mark missing evidence as pending in the index rather than fabricating documents, IDs, architecture or passing tests. Do not claim the entire application is documented after reviewing one feature page.
5. For authorized publication, read current content/revisions, follow provider formatting and applicable space guidance, and use guarded updates where supported. Preserve rich content, existing history and unrelated material. Reconcile concurrent edits instead of overwriting them. Re-read the saved documents, verify the required content and index links, then report actual URLs/paths, revisions, changes and remaining gaps. Otherwise deliver reviewable drafts without claiming publication. Source access failures follow the shared MCP connection guidance.

End with the canonical knowledge-base location, updated concern index, accepted decisions/supersession, criterion-to-evidence coverage, verification performed and unresolved decisions. Include a dated change record and a short handoff referencing durable sources so another supported assistant can resume without chat history. Perform these steps using available tools in Claude Code, Codex or Antigravity; unavailable provider actions remain explicitly pending.
